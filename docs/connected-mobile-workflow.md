# Connected mobile trip workflow

The website and phone layout use the same five-stage trip flow at `/plan`. Shared
components and scoped CSS variables live in `frontend/src/design/`; `tokens.css`
is the master visual file. Home, saved trips, Settings, planning, itinerary and map
views use the same spacing, type, surface and control conventions.

## What is connected

| Experience            | Runtime connection                                                                                                                                                                 |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Grouped questions     | Existing account-isolated version 1 draft, validation, review edits and reset. Related route/date, occupancy/budget, interests, car/timing and review questions share five stages. |
| Driving estimate      | Authenticated location resolution, explicit selection when ambiguous, then `get-initial-route`. Distance/time are provider measurements for driving only.                          |
| Paired choices        | Three pairs use exact existing reviewed 14-attribute place profiles with retained provenance. Choices feed the actual `persona_weights` sent to the planner.                       |
| Planning progress     | Cognito-authenticated `generate-final-route/stream`; real request-local worker events, heartbeat and final route. Studio visitor credentials cannot authorize this endpoint.       |
| Day-by-day schedule   | `generate-itinerary` returns actual planned visits/timing and opt-in advisory meal windows.                                                                                        |
| Saving and revisiting | Existing account-owned trip JSON, selected trip identity, saved route/itinerary navigation and explicit visited/undo state. No new table or migration.                             |
| Map and alternatives  | Existing Mapbox route map, plus authenticated bounded `route-alternatives` catalog reads. Nearby ideas have separate pins/details and retain source attribution.                   |
| Research access       | Studio/research entry points appear only in Settings after server-confirmed owner eligibility. All Studio/research HTTP routes additionally enforce the verified owner guard.      |

No chat or conversational message is generated by the flow. The interface uses
structured fields and choices. No semantic prompt is offered because this flow
has no safely connected free-text interpretation contract.

## Preferences stay behind the scenes

The first profile is the traveler's declared interests/manual amounts, preserving
legacy ratings. The second uses only exact reviewed source-profile vectors from
`docs/data/catalog-pilot-600-20261021/personas.json`, pinned by SHA-256 in the
comparison asset. These are category-based estimates, not measured personality
scores or current visit recommendations.

For each actionable pair: left/right uses that place's vector; either uses the
mean; neither uses one minus the mean. The mean of actionable vectors is normalized
independently, then averaged exactly 50/50 with the normalized first profile.
Missing/unsure-only answers reuse the first profile exactly, preserving old draft
behavior. Manual editing changes only the first profile. The final complete vector
is sent through the existing `persona_weights` contract; the backend remains
responsible for validation and CP-SAT selection.

The traveler does not see the comparison-derived profile, blended rankings or
personality charts. Internal saved metadata retains the component profiles for
consistent trip calculations; it is not presented as a traveler-facing result.

## Honest progress and failure handling

The bar represents weighted completed milestones, not an ETA or measured fraction
of provider execution. Confirmed details reach 40%; a measured base route reaches
70%; real gathering, detour, solver, schedule and final validation events advance
through 74–90%; a returned route reaches 92%; itinerary completion reaches 96%.
Only a completed itinerary plus successful persistence can produce 100%.

No elapsed-time animation invents progress. Partial route/itinerary/save failures
retain useful results and offer the relevant retry. A new itinerary invalidates
the old saved milestone until its own save succeeds. Cancellation, account changes,
unmounting and newer attempts block late UI/context publication. A request already
received by the server may still finish; stopping the browser wait cannot undo it.
Streaming is never automatically replayed after work starts. Only the verifier's
exact pre-stream authentication rejection allows one credential-renewal retry.

## Meal-window assumptions

New guided trips explicitly request `include_meal_slots: true`. Existing API
callers default to false, and old stored itineraries are unchanged.

- Breakfast: 07:00–09:00 local time.
- Lunch: 12:00–14:00 local time.
- Dinner: 18:00–20:00 local time.

Windows have stable local-date/meal IDs and no venue, price, coordinates or
reservation. They are shown separately from physical stops and do not count as
visited stops. No meal duration is reserved, no route delay is inserted and no
existing arrival/departure time is changed. Windows may overlap driving or visits;
the interface states they are open planning windows requiring adjustment.

The first known IANA timezone for a day is used, with preceding/start timezone
fallback; local ZoneInfo rules handle DST. Fully elapsed windows before known
departure or after an authoritative final arrival are omitted. Partial overlap
retains the full advisory window. A trip end is not inferred from the last
attraction/hotel. Unknown legacy fallback dates do not manufacture meal windows.
The defaults are an initial product choice; configurable windows and solver-reserved
meal breaks are separate work.

## Map, alternatives and visited state

Route geometry uses `[longitude, latitude]`; stop/alternative API coordinates use
`[latitude, longitude]`, with conversions at explicit boundaries. Mapbox attribution
remains visible. Missing token/geometry/provider errors produce a clear fallback.
`VITE_LOCAL_JOURNEY=true` is a labeled local fixture schematic, not a live street map.

`route-alternatives` accepts at most eight route points and 100 exclusion IDs;
server searches are fixed to five miles and capped at twelve deduplicated places.
Existing catalog admission, source holds and calendar eligibility remain in force.
These ideas are not in the route: detour time, visit feasibility, tickets and current
availability have not been checked. Selecting an idea highlights its actual
coordinates and opens its details; it does not silently add or swap a scheduled
stop. A validated stop-swap/replanning contract remains separate work.

Visited state is explicit and reversible, stored in `ChatData.presentation` using
stable identities. The clock never marks a stop visited. Reload hydration includes
the matching historical trip log needed for persistence. Save failures keep local
changes and show a retry; successful-looking local state is not claimed as saved.
Unknown presentation metadata and historical messages are retained. The backend
explicitly accepts trip-level presentation JSON; omitted fields in older updates
preserve it, while an explicit empty presentation object, empty visited-ID list, or null can reset visit state.

New guided trips carry a stable planning UUID. Atomic create conflict handling
permits updates only for the same planning identity; a different identity returns
409 without overwriting the existing trip. The guided client alone can retry that
exact conflict, at most three POST attempts, with a fresh 48-bit numeric ID and
aligned trip/log IDs. It retains the same planning UUID and does not rerun providers.
Legacy callers with no planning identity retain their existing same-record behavior.
This conditional SQL contract is covered by transaction/cursor doubles; actual
PostgreSQL concurrent execution was not exercised locally.

## Owner-only research

`eschiffler1122@gmail.com` is the existing server-owned eligibility constant. The
server verifies an access token, a separately signed ID token from the configured
issuer/client with the same subject, and an exact verified email claim. A browser
email string, forged token, old Studio session or study capability cannot grant
access. Studio sessions and per-study capabilities remain separately required
where applicable, preserving legitimate saved research and account permissions.

Home/header/ordinary trip navigation contain no research entry points, including
for the owner. Settings uses the trusted `routing-settings` capability; direct
Studio URLs also have authenticated frontend guards. API router guards remain the
actual enforcement boundary. Studio requests send Cognito access/ID credentials
alongside existing Studio/study headers. Logout cancels streams and prevents cached
research from resolving across sessions. No production account attributes changed.
